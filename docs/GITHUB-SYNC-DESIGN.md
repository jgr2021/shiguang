# GitHub 登录与个人记录同步：实现方案

状态：2026-10-14 已选择每人自己的私有仓库。1.9.0 预览版已实现设备登录、独立账号目录、逐条合并、冲突选择和小附件同步；真实联通与双设备验证待 GitHub App 注册完成。当前使用与限制以 [GitHub同步说明](../GitHub同步说明.md) 为准。下文保留设计背景，不代表所有远期设计均已实现。

## 用户得到什么

- 在「设置 → 账号与同步」点击「用 GitHub 登录」，在 GitHub 官方网页授权。
- 同一个 GitHub 账号在另一台电脑登录后，可取得自己的日记、待办、附件及日期关联。
- 不同账号各有独立资料空间。退出、换号时清空当前界面的记录与助手上下文，重新加载对应账号的资料。
- 没有网络时继续记录，先保存本机；联网且应用运行时再补传。同步状态明确显示「已保存到本机」「等待联网」「正在同步」「已同步」或「有冲突需要处理」。
- 不需要 GitHub 的用户继续使用本地模式。

## 存储方式待选择

| 方式 | 如何保存 | 适用范围与限制 |
| --- | --- | --- |
| 每人自己的 GitHub 私有仓库 | GitHub App 只获得使用者指定的数据仓库权限；记录按条同步，附件按内容去重 | 适合先实现文字和少量小附件同步；无需运营日记存储服务器，但首次需建立私有仓库并授权，Git 历史会保留旧版本 |
| 拾光专用云端 | GitHub 用于登录；后端按用户身份保存记录，附件放私有对象存储 | 更适合面向普通用户的长期产品；需要部署认证服务、数据库及文件存储，制定配额、备份和删除策略 |

第一种可作为轻量试用方案。第二种更容易实现一次登录、自动建立空间、大附件上传和可管理的数据删除。GitHub 登录本身不会自动提供这些存储功能。

## 账号与本机数据

1. 使用 GitHub 返回的稳定用户 ID 作为账号标识，不以可修改的用户名或邮箱作为主键。
2. 保留现有本地资料。首次登录后展示导入范围与目标账号，由使用者选择「将本机记录加入此账号」或「使用独立空间」，不能把已有资料自动上传给刚登录的账号。
3. 新账号数据放入独立目录，例如 `<数据目录>/accounts/github-<用户ID>/`。迁移使用一致性快照，成功后记录明确的旧目录与新目录映射；本聊天 Agent 访问路径也要协调。
4. 退出只撤下当前会话与凭据；保留本机副本供之后使用。账号切换前保存编辑中的日记、停止旧账号后台同步，关闭或重建读取旧资料的窗口。
5. 本机目录隔离是应用层隔离；共享同一个 Windows 登录账号的人仍可能通过文件系统访问这些文件，不应把它宣称为本机加密保险箱。

## 同步范围

| 内容 | 处理方式 |
| --- | --- |
| 每日日记 `planner_notes` | 同步日期与原文；同步不等于提交给日记 Agent 归档 |
| 待办 `planner_tasks` | 同步用户保存的日期、时间、标题、完成状态；同步程序不自行改期或完成 |
| 正式档案及修订 | 保留原文、分析版本、修订原因与来源关联；引用关系必须完整 |
| 复盘及外部动态 | 与其实际来源记录一起同步，保留版本 |
| 附件与日期关联 | 元数据与实体分别传输；附件按 SHA-256 去重并校验完整性；未传完明确标注 |
| 助手历史 | 后续可作为单独开关，不混入日记；未确认的 AI 日程草案不自动执行 |
| API Key、Codex 登录、GitHub Token | 仅留在本机凭据存储，不随记录或备份同步 |
| Agent 协议、自动任务配置、本机路径、错误日志 | 不进入跨账号同步包 |

现有 `PlannerStore.backup()` 包含本聊天配置与协议，不可直接把完整备份上传为个人同步载荷；同步必须使用字段白名单。

## 同步算法与冲突

- 本机 SQLite 仍为离线工作库。同步载荷按记录导出，不能用云端数据库文件整体覆盖运行中的 SQLite。
- 记录使用稳定 ID、内容指纹、设备 ID 和同步基线；不要仅靠设备时钟判断谁更新。
- 先取得远端当前版本，再比较本机、远端、上次同步基线：仅一侧变化则应用；不同记录各自变化则合并；同一记录双方变化则保存两个候选版本供用户选择。
- 删除使用明确的删除标记。网络错误、下载不完整、读取权限丢失都不能被解释为远端删除。删除与修改同时发生时也要进入冲突处理。
- 附件先上传并校验，再公布引用它的记录；分批传输、有限并发、失败重试。元数据已到但实体未下载时，界面显示「待下载」。
- GitHub 方案以一次提交发布一批完整变更，并以非强制分支更新检测并发；失败后重新读取、重新合并，不强推覆盖其他设备的新提交。
- 本地应用同步结果时使用事务与版本检查。后台网络请求期间不持有长时间写锁，也不阻塞 Tk 主线程。
- 自动同步合并短时间内连续编辑，遵守限流和退避；失败保留本机记录。应用关闭期间不能声称持续同步。

## GitHub 私有仓库方案的授权

- 由拾光维护者一次性注册可供其他账号安装的 GitHub App。普通使用者只完成登录与安装授权，不自行创建开发者应用或填写 Client Secret。
- 桌面端可使用 GitHub 官方 Device Flow，发布包只包含公开的 Client ID 和 App 名称，不包含开发者私钥或 Client Secret。
- 仓库权限最小化为指定仓库的内容读写与必要元数据读取；避免使用拥有全部私有仓库访问能力的传统 OAuth `repo` scope。
- 每次绑定和同步都核对仓库 ID、所属用户 ID、私有属性及数据格式标识。拒绝公共仓库和产品源码仓库作为日记同步目标。
- GitHub App 用户令牌通常有有效期。必须实现过期后的重新授权；若产品需要无感续期，应配置安全的服务端令牌代理，不能把 Client Secret 打包到桌面端。
- Git 仓库中的旧提交可能继续保留已删除记录。普通同步删除不等于清除历史；启用前要在产品隐私说明中讲清楚。仓库私有也不等于端到端加密。
- 大附件更适合文件存储服务。GitHub 普通仓库阻止超过 100 MiB 的文件，官方也不建议把 Git 当作通用备份工具；产品需有明确的小附件策略与容量提示。

## 现有代码接入位置

- `settings_ui.py`：增加「账号与同步」设置卡片，主界面不堆放额外入口。
- `app_config.py` / 新账号模块：本机凭据与账号目录选择；不与 AI Token 混用。
- `planner_store.py`、`file_store.py`、`diary.py`：增量导出、同步基线、删除标记与事务导入。
- 新同步模块：传输、版本比较、冲突保留、限流重试；与 UI 分开。
- `desktop_app.py`、`ui_extras.py`：后台调度、刷新与账号切换生命周期；任何异步结果都必须核对所属账号，禁止旧账号任务写入新账号空间。
- 三种语言文案、隐私说明、打包文件白名单同步更新。

## 接通前需要的条件

1. 确定记录使用私有仓库还是专用云服务。
2. 注册真正属于拾光的 GitHub 应用，获得公开 Client ID；专用云服务方案还需部署地址与服务端配置。
3. 完成上述实现后，使用隔离示例档案验证双设备、换号、断网、并发、令牌过期与删除行为，之后才启用真实资料同步。此文档不代表已通过这些验证。
